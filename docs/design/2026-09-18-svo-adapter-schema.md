# Restore the SVO Adapter schema and Hasura tracking

## Status

Implemented

## Objective

Add the missing PostgreSQL migration and Hasura metadata for the SVO Adapter's
`adapter` schema so the deployed `/transform-specs` and `/data-objects` routes
can query their registry tables successfully.

## User need

The deployed SVO Adapter UI is reachable and `/health` returns 200, but its
registry requests return HTTP 500 because Hasura's `query_root` does not expose
`adapter_transform_spec` or `adapter_data_object`. The adapter needs its
persistent registry schema restored before the UI and planner can operate.

## Current code/system summary

- `svo-adapter-service/app/hasura.py` queries and mutates adapter-owned tables
  through Hasura GraphQL.
- `svo-adapter-service/app/main.py`, `app/edges.py`, and `app/poller.py` use
  nine adapter tables: data objects and variables, transform specs and
  contracts, transform edges, readiness assessments, workflow plans, workflow
  runs, and provenance events.
- The adapter SQL migration and Hasura metadata were missing at investigation
  time; this spec now records their restored repository state.
- The Tapis dev deployment uses a persistent PostgreSQL volume. Its application
  rollout path must apply migrations before Hasura metadata is applied.

## Proposed design

1. Add one forward migration under `graphql_engine/migrations/` that:
   - creates the `adapter` schema;
   - creates the nine adapter tables required by the current service queries;
   - uses text IDs with database defaults compatible with Hasura nested inserts;
   - adds foreign keys, delete behavior, uniqueness constraints, and indexes;
   - keeps adapter data isolated from `modelcatalog_*` tables while retaining
     text references to model-catalog IDs.
2. Add matching Hasura metadata entries for all nine tables, including the
   relationships required by nested inserts and planner reads.
3. Add focused schema validation tests that parse the migration/metadata and
   assert the required table names, columns, relationships, and GraphQL query
   fields are present.
4. Update the deployment runbook with the exact migration/metadata apply order
   and a read-only smoke query for `adapter_transform_spec` and
   `adapter_data_object`.
5. Do not alter `.env`, run destructive SQL, or push/merge changes as part of
   this implementation pass. The live forward migration and metadata apply are
   separate operational actions requiring explicit approval.

## API/schema changes

New PostgreSQL schema: `adapter`.

Tables:

- `adapter_data_object`
- `adapter_data_object_variable`
- `adapter_transform_spec`
- `adapter_transform_contract`
- `adapter_transform_edge`
- `adapter_readiness_assessment`
- `adapter_workflow_plan`
- `adapter_workflow_run`
- `adapter_provenance_event`

The GraphQL names are generated by Hasura as `adapter_<table_name>` and match
the existing service queries. No public REST route or request payload changes
are planned.

## Data flow

```text
PostgreSQL migration
        ↓
adapter tables + indexes + constraints
        ↓
Hasura metadata tracking/reload
        ↓
SVO Adapter HasuraClient
        ↓
/transform-specs, /data-objects, planning, workflow tracking
```

## Risks and tradeoffs

- The migration targets a persistent dev database; it must be applied before
  metadata and verified without dropping existing public/model-catalog data.
- The adapter code has evolved ahead of its database migration, so the schema
  must include all columns referenced by current GraphQL documents, not only the
  two routes currently failing.
- Adapter IDs remain text to preserve fixture IDs and URI-capable identifiers;
  generated IDs use UUID text defaults for rows created by Hasura.
- Hasura permissions remain intentionally minimal because the adapter service
  uses its configured admin secret for adapter reads/system writes. Direct
  user-facing Hasura access is not introduced by this change.
- Rollback drops only the adapter schema and is therefore destructive to any
  adapter rows; it must not be used after live data is registered without an
  explicit recovery decision.

## Alternatives considered

- **Patch only the two failing queries:** rejected because planning, writes,
  edge recomputation, and run polling require the rest of the adapter schema.
- **Store adapter data in `public`:** rejected because the service boundary and
  documentation define an isolated `adapter` schema.
- **Create tables manually in the live database:** rejected as the primary fix;
  schema must be versioned and reproducible through migrations and metadata.
- **Use demo mode in production:** rejected because it discards persistence and
  does not support the live MINT/CKAN/Tapis flows.

## Test plan

- Parse the migration SQL and assert all nine tables plus required constraints
  and indexes are present.
- Parse `tables.yaml` and assert every adapter table is tracked with the
  required nested relationships.
- Run the existing SVO Adapter test suite in demo mode.
- Compile the adapter Python modules.
- When an authorized dev deployment is available, run:
  `hasura migrate apply`, `hasura metadata apply`, `hasura metadata reload`,
  then a read-only GraphQL smoke query for both registry fields.
- Verify `/health`, `/transform-specs`, and `/data-objects` after deployment.

## Documentation plan

Update `docs/deploy/mint-dev-pods.md` with the adapter schema migration,
metadata application order, smoke query, and the warning that rollback drops
adapter data only when explicitly chosen.

## Rollout/rollback plan

Repository rollout: add migration, metadata, tests, and runbook changes. Apply
the migration to the dev database only through the approved Hasura migration
workflow, then apply/reload metadata and restart or recheck the SVO pod.

Rollback before live application: revert the repository changes. Rollback after
live application requires an explicit decision; the down migration drops the
adapter schema and loses adapter registry/planning/provenance rows, so restoring
the previous application image alone is safer.

## Open questions

- Whether the existing dev deployment workflow should reintroduce automatic
  Hasura migration/metadata synchronization for future schema changes, or keep
  that operation as a separately approved deployment step.
- Whether adapter tables should later receive row-level permissions rather than
  relying on the service admin secret.

## Decisions

### 2026-09-18 - Version the missing adapter schema

- **Decision:** Add the adapter schema as a first-class Hasura migration and
  metadata change in this repository.
- **Reason:** The live failure is caused by missing GraphQL fields, and no
  reproducible schema definition currently exists.
- **Alternatives rejected:** Query workarounds, demo mode, and manual-only SQL.
- **User feedback:** User explicitly requested implementation after confirming
  the schema diagnosis.
- **Impact on implementation:** Repository changes include SQL, Hasura
  metadata, focused tests, and deployment documentation.

### 2026-09-18 - Keep live deployment separate from repository delivery

- **Decision:** Apply the verified forward migration and metadata directly to
  the Tapis dev Hasura service when explicitly authorized, without requiring a
  repository PR first.
- **Reason:** The user authorized the live repair after local validation, and
  the existing pod already contained the Hasura CLI and database connection.
- **Alternatives rejected:** Applying unverified SQL directly to the persistent
  dev volume, or waiting for a PR before restoring the already-deployed
  service's schema.
- **Impact on implementation:** Migration `1771300000000` and metadata were
  applied on 2026-09-18; Hasura reported consistent metadata and the SVO
  endpoints recovered. Repository changes remain available for the durable,
  reviewable fix.
