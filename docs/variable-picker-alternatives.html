MINT · Register Model · PR #40 follow-up

The Standard Variable picker is a flat list of machine syntax.
Here are three ways out.

PR #40 added domain grouping and ranked search — real progress. But the underlying problem is deeper than ordering: the picker shows raw CSDMS/SVO grammar, lists the same concept five or six times, and hides the one relationship that actually helps a scientist — the units a variable is really used with.

Source live data, feat/standard-variable-picker-ux 599 SV records 739 presentations 90 units

01What the data actually looks like

1 · Machine syntax, never humanized

Rows read atmosphere_air__daily_max_of_temperature. The __ separates phenomenon from property; ~ and _ are grammar. Scientists shouldn't have to parse it.

2 · The description repeats the label

Every row's secondary line begins with the label again — air__temperature This variable has… — leading whitespace and all. Pure noise.

3 · The same concept, five times

pore_water__pressure appears 6×, land_surface__elevation 5× — distinct URIs, identical to the eye. same_as is empty, so nothing reconciles them.

4 · Relationship the UI ignores → units

Each record links to variable_presentations, and those carry units. land_surface_air__temperature is used with K and degC; precipitation with mm h⁻¹ / mm day⁻¹ / m day⁻¹. Picking a variable could pre-fill the Unit field.

02Three alternatives, same data

Each mockup below is rendered from the real variable list. They escalate in ambition — from a drop-in re-render to a relationship-driven flow. Switch between them:

Humanized, concept-collapsed rows

low effort · high impact

Keep the exact same popover the PR built. Change only what each row renders: parse the CSDMS grammar into a readable name + an object chip, collapse repeated labels into one concept, drop the redundant description, and show the units it's used with as a quiet hint.

Ceiling

Still a single narrow column. Browsing 400 concepts by scroll is tiring; great for "I know the name", weak for "show me what's available".

Two-pane faceted browser

medium effort

Promote the picker to a wide dialog. A left rail facets by phenomenon domain (derived from the object root — no schema change); the right pane is the humanized list with room to breathe and no truncation. This is the documented "two-pane faceted browser" follow-up from the PR, drawn concretely.

  • Browse before you search. Pick Atmosphere & Climate or Channel & Streamflow first; the list shrinks from 400 to ~30. Facets carry live counts.
  • Width. Full names, descriptions and unit chips fit without the … truncation that plagues the popover.
  • Same row design as A. The humanized row is reused — A and B share one component.

Cost

Unit-aware guided flow

higher effort · biggest payoff

Exploit the relationship directly. The user picks a phenomenon, then a property — the two halves of the CSDMS grammar — so 400 strings become two short lists. On resolve, the flow reads the variable's presentations and offers the units it has actually been used with, wiring the Standard Variable and Unit fields together.

What changes

  • Two short lists, not one long one. Choose SOIL WATER → see only its ~7 properties. The grammar becomes the navigation.
  • Units come for free. Resolve soil_water__volume_fraction and the flow surfaces m³ m⁻³ and % — the units real presentations use — as one-tap choices for the Unit field.
  • Duplicates dissolve. A concept is one node here by construction; the resolver picks the canonical record behind the scenes.
  • Escape hatch. A "can't find it? search all" link drops back to alternative A's flat search.

Why

Directly answers the relationship you flagged: it turns the orphan Unit picker into a guided, pre-filled choice and makes the 600-row problem structurally disappear.

Cost

Most build + relies on grammar parsing being clean (the ~50 human-named oddballs like Flame Length need the search fallback).

03The hard part — choosing a unit

You flagged it and you're right: in B and C the unit was buried. The root cause is in the data — modelcatalog_unit is only id + a cryptic label like m s-1 or day/m^(1/3). No name, no dimension. So the unit picker inherits every problem the variable picker had, with none of the grammar to lean on. Two moves make it findable.

Move 1 — the variable already knows its units

For the 264 variables with a unit on record, this is the whole interaction: one tap. No searching the list of 90 at all. The suggestions come straight from the variable's variable_presentations.

Move 2 — search all units, grouped by dimension + named

The fallback (and the only path today) becomes legible: a one-time client map turns degC into degrees Celsius · Temperature, and the variable's own units float to the top, tagged SUGGESTED. Dimension grouping also lets us flag unit/variable mismatches (a temperature in metres) — the consistency check the SVO model calls for.

Recommendation — ship them in order

They're not mutually exclusive. They share one humanized row component and one resolver; each is the foundation for the next.

Now · with PR #40

A — Humanized rows

Render-layer only. Land the grammar humanizer, concept-collapse, and clean descriptions on the existing combobox. Immediate relief, no new UI.

Next

B — Faceted dialog

Reuse A's row in a wide two-pane dialog for browsing. Add the phenomenon→domain map. Handles the "show me what's there" job A can't.

Then

C — Unit-aware flow

Wire variable → presentations → units so picking a variable suggests its units. The structural fix; also a data-quality forcing function (populate same_as).

Parallel track — data hygiene

176 duplicate rows and empty same_as are a data problem the UI is papering over. Collapsing in the client is a patch; populating same_as (or merging orphan records with no presentations) fixes it at the source and makes every alternative simpler.

Parallel track — clean descriptions

The "label repeated + leading whitespace" descriptions are bad source data. A one-time ETL trim removes the noise everywhere, not just in this picker.
