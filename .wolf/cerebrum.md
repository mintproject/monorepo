## Key Learnings

- **Project:** mint — scientific modeling platform; unified catalog of models, datasets, variables, plus execution.
- **UI executions render path:** `ui/src/screens/modeling/thread/mint-runs.ts` reads `_executions[modelid].executions` populated by `executions_for_thread_model.graphql`, which JOINs through the `thread_model_execution` junction. Missing junction rows → indefinite "Downloading software image and data..." spinner at line 538 even when execution.status=FAILURE.
- **Tapis submission failure chain:** `TapisExecutionService.submitExecutions` → `processExecutionSeeds` (per-seed try/catch → `handleSingleExecutionFailure` sets FAILURE, increments failed_runs, decrements submitted_runs) → `handleSubmissionResults` throws "All jobs failed" if every seed failed → outer catch → `handleSubmissionFailure` → `handleFailedConnectionEnsemble` (deletes+reinserts summary, inserts thread_provenance event). Both handlers run for all-failed case.
- **Status mapping:** `TapisExecutionService.mapStatus` translates `jobs.JOB_NEW_STATUS.*`: FAILED/CANCELLED/PAUSED → FAILURE; FINISHED/ARCHIVED/SUCCESS → SUCCESS; PENDING/PROCESSING_INPUTS/STAGING_*/SUBMITTING_JOB/QUEUED → WAITING; RUNNING/ARCHIVING → RUNNING.
- **Tapis webhook URL validation:** Tapis Notifications rejects URLs via `NTFLIB_DLVRY_ADDR_NOT_URL` before reachability check. RFC 6762 reserved TLDs (`*.local`) fail. `TapisJobSubscriptionService.generateWebHookUrl` uses `prefs.tapis_webhook_base_url` first (trailing slash trimmed), falls back to `${prefs.ensemble_manager_api}/tapis`. Prod (`dynamo/shared/values.yaml`) leaves override UNSET → fallback derives correct URL from FQDN ingress. Dev (`helm-charts/dynamo-values.yaml`) keeps `webhook.site/<uuid>` override since mint.local cannot receive (bug-012 workaround, still valid). See bug-076.
- **Stuck-spinner fix verification:** Always test on a FRESH thread. Pre-fix orphans (status=FAILURE, no junction) won't auto-recover on re-submit because `prepareModelExecutions` → `deleteThreadModelExecutionIds` wipes all junction for tm_id then `createExecutions` inserts fresh. Manually reinsert junction via Recovery section in `docs/debug-tapis-execution.md` for stale orphans.
- **Junction-deleting mutations (audit list):** Six compiled mutations in `mint-ensemble-manager` dist/server.js delete `thread_model_execution`: `new_executions` (no-op for new IDs), `delete_executions`, `delete_thread_model_executions`, `delete_thread_model_by_config`, `update_thread_data`, `update_thread_model`. Plus fixed `handle_failed_connection_ensemble`. Search this set first when debugging stuck-spinner.
- **Hasura admin query from inside cluster:** Use `wget --post-file=` (BusyBox alpine has no curl). Pipe JSON via stdin: `cat q.json | kubectl exec -i <pod> -c head -- sh -c 'cat > /tmp/q.json'` then `kubectl exec <pod> -c head -- sh -c 'wget -qO- --header="x-hasura-admin-secret: ..." --header="Content-Type: application/json" --post-file=/tmp/q.json http://mint-hasura/v1/graphql'`. Admin secret in `HASURA_GRAPHQL_ADMIN_SECRET` env on ensemble-manager pod.
- **ModelCatalogResource lazy-fetch wipes junction columns:** `ui/src/screens/models/configure/resources/resource.ts` `setResources()` (line 1419) stores inline parent payload in `_resources` but then calls `resourceApi.get(id)` per row, storing entity GET response in `_loadedResources[id]`. Both render (lines 479, 513) and `getResources()` (line 1642) read `_loadedResources`, NOT `_resources`. Junction-only fields (e.g. `isOptional` on modelcatalog_configuration_input) get dropped. Subclasses must capture inline overlay before `super.setResources()` and re-merge into `_loadedResources` via `requestUpdate()` override + sync overlay on user edits. See `ModelCatalogDatasetSpecification._junctionOverlay`.
- **Tapis fileInput ↔ model.input_files join is by NAME (brittle):** `TapisJobService.createJobFileInputsFromSeed` (`TapisJobService.ts:110`) does `model.input_files.find(i => i.name === fileInput.name)`. Name drift between Tapis app `jobAttributes.fileInputs[].name` and model-catalog `input_files.name` → "Component input not found for <name>". Keep names identical in Hasura. Real fix: join by `component.inputs[].id` ↔ `model.input_files[].id` or by position. See bug-065.
- **Thread page bypasses REST API for model inputs:** Thread datasets/runs UI consumes `ui/src/queries/thread/get.graphql` (and `get-subscription.graphql`) via Apollo directly against Hasura, NOT the v2 model-catalog REST API. Junction columns (`modelcatalog_configuration_input.is_optional`, etc.) must be selected explicitly in those `inputs { ... }` blocks AND mapped through `ui/src/util/graphql_adapter.ts:495` (`m.input_files = (m["inputs"] ?? []).map(item => ({ id, name, variables, isOptional: !!item.is_optional }))`). REST plumbing (sdk-patches, custom-apis/model-configuration*.ts) does not help here. Any new junction column added in Phase 12+ must touch BOTH paths or thread-page features will silently ignore it. See bug-081.
- **ModelConfiguration write path requires nested DatasetSpecification objects:** `Configuration.hasInput`/`hasOutput` FK targets `DatasetSpecification`, NOT `VariablePresentation`. Sending VP id directly → `modelcatalog_configuration_input_input_id_fkey` violation. Working write shape: `POST /modelconfigurations` with `hasInput: [{id: <existing_DS_id>, type:["DatasetSpecification"], label:[...], ...}]`. Use existing DS only — `POST /datasetspecifications` is broken with same `Not-NULL violation. label` cascade as ModelConfiguration. Real chain: `Model → hasVersion → SoftwareVersion → hasConfiguration → ModelConfiguration → hasInput → DatasetSpecification → hasPresentation → VariablePresentation`. Cannot wire MODFLOW-2000 VPs to SVO query end-to-end without DS create being fixed upstream. See `dynamo-experiment-may/tests/modelconfig_writepaths_results.json`.
- **Cascade null-label bug — fixed (bug-087, 2026-05-07):** `POST /modelconfigurations|/modelconfigurationsetups|/datasetspecifications` with any relation field returned 400 `null value in column "label"`. Real cause was NOT flush ordering. `buildJunctionInserts` (`model-catalog-api/src/mappers/request.ts:227`) emitted `on_conflict.update_columns:['label']` on the **nested target-entity** insert. When a client linked an existing target by id alone (`hasInput:["uri"]` or `[{id:"uri"}]`), `nestedData` was `{id}` only; on Hasura PK conflict the existing target row got `UPDATE label=NULL` → not-null violation. Outer junction already used `update_columns:[]` — inner inconsistency was the bug. Fix: change to `[]` (link-or-noop). Regression coverage in `src/mappers/__tests__/request.test.ts`. Distinct/orthogonal: PUT path inserts junction flat with `input_id=<vp_id>` but FK targets `dataset_specification` — VP id still hits a real FK violation; resolve by passing DS id, not VP id.

## Do-Not-Repeat

- [2026-04-26] Failure-cleanup mutations must not delete `thread_model_execution` junction rows without re-inserting them. UI joins through that junction; deletion strands FAILURE rows → indefinite spinner. See bug-011, `handle-failed-connection-ensemble.graphql`.
- [2026-04-26] Never derive Tapis webhook URLs from cluster-internal `*.local` hostnames. Validator `NTFLIB_DLVRY_ADDR_NOT_URL` rejects RFC 6762 reserved TLDs pre-reachability. Use `tapis_webhook_base_url` override in dev (webhook.site); reserve `ensemble_manager_api` fallback for FQDN-ingress envs. See bug-012.
- [2026-05-03] Never set `tapis_webhook_base_url` to a Tapis API host (e.g. `https://portals.tapis.io`). It is the WEBHOOK RECEIVER URL (where Tapis POSTs events TO ensemble-manager), not the Tapis API base. Both names contain "tapis" — easy to confuse. Prod: leave UNSET so code fallback `${ensemble_manager_api}/tapis` derives the receiver from the ingress FQDN. Override only for dev with ngrok-style public tunnel. See bug-076.
- [2026-04-27] Never commit phase/feature work directly on `main`/`master`. Create feature branch (e.g. `gsd/phase-{N}-{slug}`) before first phase commit, in BOTH superproject AND any submodule receiving phase commits. Applies regardless of `branching_strategy: none`.
- [2026-05-01] "Component input not found for X" = name drift between Tapis app `fileInputs[].name` and model-catalog `input_files[].name`. Check both sides match in Hasura before code-diving. See bug-065.
- [2026-05-03] When adding a new junction column to model-catalog (e.g. `modelcatalog_configuration_input.is_optional`), wiring REST API + sdk-patches + ensemble-manager is NOT enough. Thread page reads via Apollo `get_thread`/`get_thread_subscription` directly against Hasura. Must also: (1) select column in `ui/src/queries/thread/get.graphql` + `get-subscription.graphql` inside the relevant junction block; (2) map it in `ui/src/util/graphql_adapter.ts` `m.input_files`/`output_files`/`input_parameters`; (3) extend the matching ModelIO/ModelParameter interface in `ui/src/screens/models/reducers.ts`. Otherwise thread-page UI silently drops the column. See bug-081.
- [2026-05-03] Hasura → ModelOutput shape mismatch in mint-ensemble-manager: GraphQL query `getModelOutputGQL` returns `outputs[].output.{id,label,has_format}` (DYNAMO v2.0 Hasura) but `getModelOutputsByModelId` is typed `Promise<ModelOutput[]>` (`{position, model_io:{id,name,format,variables}}`). Always map at the GraphQL boundary — do NOT return raw Hasura rows where downstream code reads `model_io.name`. Use the pure mapper `mapHasuraOutputsToModelOutputs`. Test fixtures already follow ModelOutput shape, so unit tests pass while production crashes. See bug-077.
- [2026-05-07] Hasura nested insert `on_conflict.update_columns` on a target-entity link MUST be `[]`, not a column subset like `['label']`. When the client links by id only, the nested insert object lacks the column, and on PK conflict Hasura overwrites the existing row's column with NULL → not-null violation. Use `update_columns:[]` for pure link-or-noop semantics. New rows still insert with all supplied fields; on_conflict only triggers when the target already exists. Renames go via the target's own PUT, not via parent POST. See bug-087.
