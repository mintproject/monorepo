# GAM DFC Planner UI

## Status: Implemented

## Objective

Replace the SVO Adapter UI entries for WERC InSAR ETL and MINT Catalog with a question-first GAM DFC evaluation demo that plans DFC metric extraction from CKAN-hosted TWDB GAM modeled outputs.

## User need

Water planners, GMA board members, and TWDB users should be able to start from the planning question: "I'm in X GMA; what are the Desired Future Conditions and are we expected to meet them based on the model?" They should not need to understand SVO contracts, actor transforms, CKAN resources, or workflow plans before the demo gives them a clear answer path.

## Current code/system summary

- The bundled SVO Adapter UI is `static/index.html`.
- It now has visible tabs for `DFC Evaluation` and `NTGAM Subsidence Forecast`.
- Backend support already exists for CKAN data-object sync through `POST /admin/sync-from-ckan`.
- Backend support already exists for DFC transform registration through `POST /admin/seed-gma-dfc`.
- `examples/gma_dfc_transforms.json` already covers head/drawdown, saturated thickness, spring flow, and stream flow transforms from MODFLOW HDS/CBC modeled outputs.
- `examples/twdb_adopted_dfc_2021.json` stores adopted DFC target records extracted from TWDB's 2021 adopted DFC PDF, with source page and text-line provenance.
- `twdb-gis-datasets` now has CKAN resources for TWDB GMA, GCD, and county boundary shapefiles plus live ArcGIS boundary layers.
- `POST /plans/model-run` already handles multi-input Tapis/MINT-style planning, which is the right surface for later DFC compliance runs that need modeled output + boundary geometry + target records.
- The final `dfc_compliance` task code is still a stub, so the initial UI should avoid overstating final compliance-report execution.

## Proposed design

Keep the NTGAM forecast tab as a secondary demo. Remove WERC and MINT Catalog tabs from the UI and make `DFC Evaluation` the default demo tab.

Boundary resources and DFC geometry transforms should follow the existing MINT pattern instead of becoming a FastAPI geometry endpoint:

- CKAN resources carry `mint_standard_variables` and boundary metadata.
- `POST /admin/sync-from-ckan` maps those CKAN resources into adapter data objects.
- MINT-style transform specs describe boundary query/normalization and DFC area preparation.
- Tapis/geo_actor performs ArcGIS query, geometry conversion, intersection, clipping, and aggregation.
- FastAPI remains a planner/catalog adapter and does not perform geospatial ETL inline.

The DFC tab will:

- Make `DFC Evaluation` the default visible demo.
- Put the planner-facing question in the first viewport: GMA, aquifer, target year, model scenario, and DFC metric.
- Make aquifer, target year, and metric choices adaptive to the selected GMA using the adopted DFC target records.
- Default the advanced GMA boundary source to TWDB's live GMA ArcGIS layer and query it by `GMAnum` for the selected GMA at workflow runtime.
- Show an `Answer` section with DFC metric cards for drawdown/head, saturated thickness, spring flow, and streamflow.
- Report whether each metric has a modeled-output calculation path.
- Show adopted DFC targets from the PDF-derived fixture when they match the selected GMA/aquifer/metric.
- Avoid claiming final meet/not-meet compliance until a modeled value is run and compared against the adopted target.
- Move CKAN sync, transform registration, data-object source lists, and `/plans` graph details into evidence/data-readiness sections below the primary answer.
- Keep dry-run Tapis workflow generation available for the selected DFC metric.

## API/schema changes

No schema changes.

Add read-only endpoint:

- `GET /dfc-targets?gma_id=GMA%2012&aquifer=Carrizo-Wilcox&metric=drawdown`

The endpoint reads `examples/twdb_adopted_dfc_2021.json` and filters adopted
DFC target records by GMA, aquifer/system, metric, and optional area. It does
not mutate Hasura, CKAN, Tapis, or MINT state.

Add no geometry-computation endpoint. Boundary discovery should come from synced
adapter data objects and `/data-objects`; execution should be represented as
Tapis/MINT transform specs and multi-input plans.

## Data flow

1. User opens `DFC Evaluation`.
2. In demo mode, the UI seeds the in-memory GMA DFC fixture.
3. User enters the GMA, aquifer, target year, scenario, and metric scope.
4. UI calls `GET /dfc-targets` to load adopted target records for the selected GMA/aquifer.
5. UI chooses the best registered modeled output for each requested DFC metric.
6. UI calls `POST /plans` for each modeled-output/DFC target contract pair.
7. UI renders planner-facing metric cards, adopted target evidence, and a summary of what can be calculated.
8. User can inspect the transform chain and generate a dry-run workflow for a selected metric.
9. In live mode, the user explicitly clicks `Load DFC transforms` and `Sync CKAN GAM resources`; CKAN sync stays dry-run by default.
10. Boundary resources are synced from `twdb-gis-datasets` when tagged with boundary `mint_standard_variables`.
11. Boundary query/geometry transforms run on Tapis/geo_actor when a modeled-output aggregation or partial-area DFC compliance plan is submitted.

## Risks and tradeoffs

- CKAN sync can create adapter data-object rows; keep it explicit and dry-run by default.
- `dfc_compliance` final report execution is not complete yet; expose it as a planned contract, but show that metric extraction is the reliable part today.
- The demo can look like a compliance determination if wording is loose; label output as ready for comparison until a modeled value is available.
- The PDF is not a tagged table; keep the extraction script and source page/line provenance with every target record.
- The extracted source PDF text does not contain GMA 5; preserve that as a data gap rather than inventing values.
- Live execution depends on Tapis auth and geo actor availability. `SVO_ADAPTER_GEO_ACTOR_ID` is the server-side default, surfaced to the UI through `GET /runtime-defaults`, and live submit falls back to it when the request omits `geo_actor_id`.
- Generated DFC workflows must declare only the Tapis args their task graph actually references; otherwise Tapis rejects DFC submissions for missing unrelated SUBSIDE/WERC args.
- CKAN catalog contents change over time; the UI should not hardcode a fixed dataset list.
- Boundary SVO names are adapter/MINT-style variables under the MINT namespace; if a formal MINT StandardVariable exists later, map aliases rather than breaking existing CKAN tags.
- Model layer remains an explicit advanced input until the adapter has GAM aquifer/layer mapping metadata for each model package.
- True partial-area DFCs require multi-input intersection of GMA, county/GCD, and aquifer boundaries; the single-source BFS path is not enough for that final step.

## Alternatives considered

- Keep MINT Catalog BFS and rename labels: rejected because the user asked to remove MINT Catalog from the UI.
- Auto-sync CKAN on page load: rejected because it mutates adapter metadata in live mode.
- Build a new backend endpoint first: rejected for this pass because existing `/plans` and sync endpoints already provide the needed planner surface.
- Compute boundary intersections in FastAPI: rejected because Tapis/geo_actor should own ETL execution, and MINT-style specs should describe how those tasks compose.
- Keep data-object and target selectors as the first screen: rejected because it is adapter-centric and does not match how planners ask the DFC question.
- Hardcode target values in the UI: rejected because target records need PDF provenance and should be reusable by tests/API consumers.

## Rollout/rollback plan

Rollout is a static UI, fixture, sync-mapping, and task-code update. Rollback
is a normal code revert for local changes. CKAN resource metadata patches require
an explicit reviewed payload and can be rolled back with `resource_patch` to
remove or correct the added metadata fields. No live Tapis runs are part of this
change.

## Open questions

- The final DFC compliance-report executor still needs production implementation against the DFC target table/CSV.
- CKAN boundary resources need the prepared `resource_patch` metadata applied before `/admin/sync-from-ckan` can discover them automatically in live mode.
- Live boundary execution depends on geo_actor support for `boundary_to_geojson` and `intersect_boundaries`.
- The adopted DFC PDF used for extraction does not include GMA 5 in the extracted text.

## Decisions

### 2026-08-12 - Replace old tabs with a DFC planner

- **Decision:** Remove WERC and MINT Catalog from the visible UI and add a DFC planner tab backed by existing CKAN sync and `/plans`.
- **Reason:** The requested workflow is GAM-modeled-output-to-DFC planning, not WERC or MINT catalog maintenance.
- **Alternatives rejected:** Rename the MINT BFS tab; auto-run CKAN sync on load.
- **User feedback:** User asked to remove WERC InSAR ETL and MINT Catalog from the UI and calculate DFCs from CKAN GAMs.
- **Impact on implementation:** Static UI changes plus focused fixture/test updates.

### 2026-08-12 - Make the DFC demo question-first

- **Decision:** Make `DFC Evaluation` the default demo view and lead with "I'm in a GMA. Are we expected to meet the DFCs based on the model?"
- **Reason:** The target audience thinks in GMAs, aquifers, target years, and DFC status, not transform contracts or catalog sync.
- **Alternatives rejected:** Keep the `GAM DFC Planner` selector-first interface; show CKAN setup before the planning question.
- **User feedback:** User clarified that the demo should serve water planners, GMA board members, and TWDB users asking whether a selected GMA is expected to meet DFCs based on modeled outputs.
- **Impact on implementation:** Static UI defaults to DFC evaluation, adds planner-facing answer cards, and moves transform/source details into evidence sections without changing backend APIs.

### 2026-08-12 - Extract adopted DFC targets from TWDB PDF

- **Decision:** Add a PDF-derived target fixture, a reproducible extractor script, and a read-only `/dfc-targets` lookup endpoint.
- **Reason:** The UI needs adopted DFC target records by GMA/aquifer to answer the planner question without hardcoding values in JavaScript.
- **Alternatives rejected:** Leave `Target comparison pending` until a future CSV exists; manually hardcode a few demo values.
- **User feedback:** User identified the `Adopted Desired Future Conditions - 2021 PDF` as the source to extract for UI setup.
- **Impact on implementation:** Adds `examples/twdb_adopted_dfc_2021.json`, `scripts/extract_twdb_dfc_targets.py`, `GET /dfc-targets`, UI target evidence rows, and focused endpoint tests.

### 2026-08-12 - Use MINT-style boundary resources and Tapis ETL

- **Decision:** Represent GMA, GCD, and county boundaries as CKAN-synced adapter data objects and represent boundary query/intersection work as MINT-style transform specs executed on Tapis/geo_actor.
- **Reason:** MINT can infer workflow composition from typed inputs, outputs, formats, units, and parameters, but DFC scope semantics must still be encoded explicitly. FastAPI should not become the geospatial ETL engine.
- **Alternatives rejected:** A bespoke `/dfc-boundaries` endpoint that performs geometry work; hardcoding boundary URLs in the UI; treating the raw boundary URI textbox as the primary UX.
- **User feedback:** User asked whether MINT provides a similar inference mechanism and then approved implementing that direction.
- **Impact on implementation:** Add boundary SVO mappings and formats to `ckan_sync.py`, DFC boundary transform specs to `gma_dfc_transforms.json`, geo_actor task-code support for boundary operations, tests, and a reviewed CKAN metadata patch plan.
