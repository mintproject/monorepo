# What Belongs in CKAN vs. the SVO Adapter

## Purpose

This document clarifies where data, logic, and state live in the DFC workflow. The
goal is to keep the system flexible beyond one decision-support use case by
maintaining clean boundaries between **scientific/reference data**, **executable
adapter logic**, **runtime state**, and **objective specifications**.

---

## The Four Categories

| Category | Where it lives | Examples |
|----------|----------------|----------|
| Scientific / reference data | **CKAN** | Model outputs (GeoTIFF, NetCDF), TWDB GIS boundary layers, TWDB adopted DFC targets (when published) |
| Executable adapter logic | **SVO Adapter** (transform registry + planning APIs) | Unit conversion specs, format conversion specs, boundary query/intersect specs, compliance-check step specs |
| Runtime / execution state | **Tapis Workflows + adapter DB** (PostgreSQL `adapter.*` schema) | Workflow plans, workflow runs, task status, provenance events |
| Objective specification | **JSON objective spec** passed to `/plans` or `/workflows/submit` | DFC compliance objective, water-budget objective, any future goal-oriented use case |

---

## Detailed Breakdown

### 1. Scientific / Reference Data -> CKAN

CKAN is the catalog of record for **byte-addressable resources** and **reference
datasets** that multiple downstream systems consume.

**Belongs in CKAN:**

- Model output files (GeoTIFF head rasters, NetCDF, binary HDS/CBC)
- TWDB GIS boundary resources (GMA, GCD, county shapefiles/feature layers)
- TWDB adopted DFC targets (when published as a dataset)
- Observation well locations, historical water-level records
- Any dataset that needs discoverability, DOI, versioning, or cross-system access

**Does not belong in CKAN:**

- Transform logic or step definitions
- Workflow plans or run state
- Objective specifications
- Compatibility edges or graph search data

**Rule of thumb:** If a human or external system would search for it, download it,
or cite it, it belongs in CKAN. If it describes *how to transform* data rather than
*what the data is*, it belongs in the adapter.

**Example -- DFC targets currently live as a fixture:**

```json
// examples/twdb_adopted_dfc_2021.json
{
  "records": [
    {
      "id": "dfc2021-0001",
      "gma": 1,
      "area": "Dallam; Moore",
      "metric": "saturated_thickness_or_storage",
      "target_values": [{"value": 40.0, "unit": "percent"}],
      "period": {"baseline_year": 2018, "target_year": 2080}
    }
  ]
}
```

This file is a **fixture** today. When published to CKAN, it becomes a discoverable
resource that any system (adapter, UI, external tools) can reference by URI.

---

### 2. Executable Adapter Logic -> SVO Adapter Transform Registry

The adapter owns the **transform registry**: the catalog of what transformations
are possible, their input/output contracts, and how to chain them.

**Belongs in the adapter:**

- `transform_spec` definitions (unit convert, format convert, boundary query, etc.)
- `transform_contract` input/output specifications
- `transform_edge` compatibility graph (precomputed or on-the-fly)
- Planning API (`POST /plans`) that searches the transform graph
- Workflow generation (`POST /workflows/generate`) that emits Tapis pipeline defs
- Readiness assessment logic (`POST /readiness/check`)

**Does not belong in the adapter:**

- The actual bytes of model outputs or boundary files
- Published datasets or their metadata
- Runtime execution state (that goes in the adapter DB or Tapis)
- The DFC objective itself (that's an input *to* the planner, not a registered transform)

**Rule of thumb:** If it describes *how to get from contract A to contract B*, it's a
transform and belongs in the adapter registry. If it *is* the data, it belongs in CKAN.

**Example -- transform spec in the registry:**

```json
{
  "id": "ts-head-ft-to-m",
  "name": "head-ft-to-m",
  "transform_type": "unit_convert",
  "method": "tapis_function",
  "contracts": [
    {"role": "input",  "standard_variable_uri": "...head", "unit": "ft"},
    {"role": "output", "standard_variable_uri": "...head", "unit": "m"}
  ]
}
```

This is *logic* -- it describes a capability, not a dataset.

---

### 3. Runtime / Execution State -> Tapis + Adapter DB

When a workflow runs, its state lives outside both CKAN and the transform registry.

**Belongs in adapter DB (`adapter.*` schema):**

- `workflow_plan` -- the planned DAG (`plan_json`)
- `workflow_run` -- execution state, Tapis run UUID, status
- `provenance_event` -- append-only audit trail
- `readiness_assessment` -- cached compatibility checks

**Belongs in Tapis Workflows:**

- Pipeline definitions (generated by `POST /workflows/generate`)
- Task execution state (Tapis manages this natively)
- File staging and I/O (Tapis storage)

**Does not belong in Tapis:**

- Transform registry metadata
- DFC target records
- Model output catalog entries

**Rule of thumb:** If it answers "what happened" or "what is happening now," it's
runtime state. If it answers "what *could* happen," it's planning/registry.

---

### 4. DFC Objective -> JSON Objective Spec

The DFC compliance question ("are we expected to meet the DFCs?") is an **objective**,
not a transform. It should be expressed as a JSON objective specification that the
adapter consumes at planning time.

**The objective is NOT:**

- A registered transform in the registry
- A CKAN dataset (though it *references* CKAN resources)
- Hardcoded in the adapter code

**The objective IS:**

- A JSON object passed to `/plans` or `/workflows/submit`
- A structured specification of *what to evaluate* and *against what targets*
- Consumed by the planner to select the right transform chain

**Example -- DFC objective spec:**

```json
{
  "objective_type": "dfc_compliance",
  "gma": 1,
  "aquifer": "Ogallala and Rita",
  "metric": "saturated_thickness_or_storage",
  "area": "Dallam; Moore",
  "area_type": "area",
  "baseline_year": 2018,
  "target_year": 2080,
  "source_model_output": "ckan://...hds_lyr8_sp132.tif",
  "dfc_targets_uri": "ckan://...twdb-dfc-2021"
}
```

This objective tells the planner: "Evaluate GMA 1, Ogallala aquifer, Dallam/Moore
area against the 2021 DFC targets." The planner then selects the appropriate
transform chain (boundary query -> intersect -> extract -> compliance check).

**Why this matters for flexibility:**

- Different use cases (water budget, spring flow, stream flow) use the same pattern:
  objective spec -> planner -> transform chain -> compliance report.
- New DFC metrics or new GMAs don't require code changes -- just a new objective spec.
- The adapter remains generic; the objective carries the use-case specifics.

---

## Decision Flowchart

```
Is it data (bytes, files, datasets)?
  -> CKAN

Is it a description of how to transform data?
  -> SVO Adapter transform registry

Is it "what happened" or "what is happening now"?
  -> Tapis / adapter DB (runtime state)

Is it "what should we evaluate and against what targets?"
  -> JSON objective spec (passed to the adapter at planning time)
```

## Concrete Examples by DFC Workflow Step

| Workflow step | Where it lives | Why |
|---------------|----------------|-----|
| GMA boundary shapefile | CKAN (`twdb-gis-datasets`) | Reference GIS data, discoverable |
| "Query GMA 1 boundary" transform | Adapter registry (`ts-gma-boundary-query`) | Executable logic, reusable across GMAs |
| DFC target: "40% storage in Dallam/Moore" | JSON objective spec (or CKAN when published) | Use-case-specific goal, not transform logic |
| "Clip head raster to GMA boundary" | Adapter registry (`ts-head-gma-average`) | Executable logic, reusable |
| Workflow plan for GMA 1 DFC check | Adapter DB (`workflow_plan`) | Runtime state, ephemeral |
| Compliance report output | Adapter DB (`workflow_run` output) + CKAN (if published) | Results may be published for reuse |

---

## Rule of Thumb Summary

1. **If it's data people want to find, download, or cite -> CKAN.**
2. **If it describes how to transform data -> SVO Adapter transform registry.**
3. **If it tracks what happened or is happening -> Tapis / adapter DB.**
4. **If it asks "are we meeting the goal?" -> JSON objective spec.**

---

## Why This Boundary Matters

The DFC workflow is one *instance* of a general pattern:

1. Start with model output data (CKAN)
2. Transform it to match target requirements (adapter registry)
3. Evaluate against objectives (objective spec)
4. Track what happened (runtime state)

By keeping these four concerns separated, the same adapter can support:

- **DFC compliance** (current use case)
- **Water budget analysis** (different objective, same transforms)
- **PumpTest evaluation** (different objective, same transforms)
- **Any future decision-support use case** that needs: data -> transform -> evaluate -> report

The adapter doesn't need to know *why* you're transforming data. It just needs to
know *what transforms are available* and *what the objective requires*. The objective
spec carries the use-case logic; the adapter carries the reusable transform logic.
